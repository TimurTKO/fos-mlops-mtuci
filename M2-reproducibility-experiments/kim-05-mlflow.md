# Лабораторная работа №5. Трекинг экспериментов и выбор модели

## Назначение

Организовать сопоставимое проведение ML-экспериментов, связать параметры и метрики с версиями кода и данных, обосновать выбор модели и зарегистрировать выбранную версию.

## Проверяемые результаты и индикаторы

- **LC-2.1, средний уровень:** проводит серию воспроизводимых экспериментов, сравнивает метрики и анализирует результат;
- **LC-5.1, средний уровень:** применяет MLflow Tracking и Model Registry как часть инженерного жизненного цикла модели.

## Исходные материалы

- результат ЛР4;
- [`scripts/run_experiments.py`](../resources/starter-project/project-baseline/scripts/run_experiments.py);
- локальное хранилище MLflow на SQLite либо предоставленный tracking server;
- [шаблон отчёта по экспериментам](attachments/experiment-report-template.md).

## Условия выполнения

Требуются Python 3.11+ и MLflow 3.x. Для базового сценария используется локальный backend `sqlite:///mlflow.db`; платные сервисы и GPU не требуются. База MLflow, локальные артефакты и служебные каталоги не публикуются в Git.

## Задание

1. Настроить MLflow Tracking и создать отдельный experiment для учебного проекта.
2. Провести не менее трёх сопоставимых запусков, изменяя один или два заранее выбранных гиперпараметра.
3. Для каждого запуска зафиксировать:
   - параметры модели и генерации данных;
   - основные метрики на независимой тестовой выборке;
   - Git commit SHA;
   - хеш или иную идентификацию версии данных;
   - артефакты: модель, файл метрик и при необходимости график/таблицу ошибок.
4. Добавить model signature и пример входных данных при логировании модели.
5. Сформулировать критерий допуска модели до анализа результатов. Минимальное условие учебного проекта: `test_f1 >= 0.70`.
6. Сравнить запуски в интерфейсе или через API MLflow и выбрать лучшую допустимую модель.
7. Зарегистрировать выбранную модель в Model Registry и назначить ей алиас `champion` либо эквивалентный статус.
8. Загрузить зарегистрированную модель по URI реестра и выполнить контрольное предсказание.
9. Подготовить краткий отчёт, в котором указаны критерий выбора, отклонённые варианты и ограничения эксперимента.

## Представляемый результат

- код запуска серии экспериментов;
- минимум три MLflow run с параметрами, метриками, тегами и артефактами;
- зарегистрированная версия модели;
- алиас или статус выбранной модели;
- отчёт о выборе модели;
- README с командами запуска tracking server/UI и воспроизведения экспериментов.

## Формат защиты

Студент показывает сравнение запусков, объясняет критерий выбора и происхождение выбранной модели. Затем преподаватель предлагает изменить порог качества или один параметр, после чего студент прогнозирует влияние на решение о регистрации.

## Оценивание — 5 баллов

| Критерий | Баллы |
|---|---:|
| Не менее трёх сопоставимых запусков с параметрами и тестовыми метриками | 1 |
| Прослеживаемость к Git-коммиту и версии данных | 1 |
| Полные артефакты модели, signature и пример входа | 1 |
| Обоснованный критерий выбора и корректная регистрация модели | 1 |
| Отчёт, воспроизводимые команды и индивидуальное объяснение | 1 |

Работа засчитывается при получении не менее 4 баллов и наличии зарегистрированной модели, происхождение которой можно восстановить.

## Типичные ошибки

- сравнение метрик, рассчитанных на разных выборках;
- выбор лучшей модели без заранее определённого критерия;
- логирование только итоговой метрики без параметров и версии данных;
- регистрация модели, не прошедшей quality gate;
- добавление `mlflow.db`, `mlruns/` или секретов tracking server в Git.

## Использование генеративного ИИ

Разрешено для подготовки черновика кода логирования и анализа ошибок. Студент самостоятельно проверяет корректность метрик, критерий выбора и происхождение зарегистрированной модели.

## Использование внешних ресурсов и командная работа

- разрешены материалы курса и официальная документация используемых инструментов;
- сторонние статьи, примеры и фрагменты кода допускаются при указании источника и самостоятельной адаптации;
- запрещено выдавать чужой репозиторий или готовое решение за собственную работу;
- секреты, токены, персональные данные и закрытый код нельзя передавать внешним сервисам;
- при командной работе каждый участник фиксирует вклад в Git и проходит индивидуальную защиту;
- преподаватель вправе ограничить Интернет на отдельном этапе защиты или выдать эквивалентный локальный материал.
