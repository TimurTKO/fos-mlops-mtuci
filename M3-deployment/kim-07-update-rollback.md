# Лабораторная работа №7. Обновление и откат ML-сервиса

## 1. Назначение

Освоить управляемый выпуск новой версии контейнеризированного ML-сервиса, проверку кандидата и восстановление стабильной версии при нарушении заданных критериев.

## 2. Проверяемые результаты

| Индикатор | Уровень | Наблюдаемый результат |
|---|---|---|
| LC-5.1 | средний | Студент собирает версионированные образы, выполняет обновление, smoke-тест и откат. |
| AI S -1.1 | базовый | Студент выявляет риск неуспешного релиза, формулирует критерии отката и документирует реакцию. |

## 3. Предварительные условия

- ЛР №6 выполнена;
- сервис запускается через `compose.yaml`;
- smoke-тест возвращает ненулевой код при ошибке;
- имеются стабильная и кандидатная версии образа;
- `.env` и локальный журнал релизов исключены из Git.

## 4. Задание

### Шаг 1. Политика версионирования

Опишите правила именования образов. Минимально используются:

- `mlops-course-api:stable` — подтверждённая версия;
- `mlops-course-api:candidate` — новая проверяемая версия;
- номер приложения, например `1.0.0` и `1.1.0`;
- версия модели, например `baseline-v1` и `baseline-v2`.

Тег, версия приложения и версия модели должны выводиться endpoint `/health`.

### Шаг 2. Стабильный выпуск

Соберите и запустите стабильную версию:

```bash
python scripts/release_manager.py build   --tag stable   --service-version 1.0.0   --model-version baseline-v1   --model-c 1.0

python scripts/release_manager.py deploy   --tag stable   --expected-version 1.0.0
```

Сохраните:

- результат smoke-теста;
- ответ `/health`;
- статус контейнера;
- запись журнала выпуска.

### Шаг 3. Кандидатная версия

Соберите кандидатную версию:

```bash
python scripts/release_manager.py build   --tag candidate   --service-version 1.1.0   --model-version baseline-v2   --model-c 0.5
```

Поясните, чем она отличается от стабильной версии и как это подтверждается технически.

### Шаг 4. Неуспешный выпуск и откат

Запустите кандидатную версию с искусственно включённым отказом:

```bash
python scripts/release_manager.py deploy   --tag candidate   --expected-version 1.1.0   --simulate-failure
```

Ожидаемый результат:

1. кандидат не проходит readiness/smoke-проверку;
2. менеджер релиза фиксирует ошибку;
3. предыдущие значения `.env` восстанавливаются;
4. Compose повторно запускает стабильный образ;
5. smoke-тест подтверждает восстановление;
6. в `release-history.jsonl` появляются события отказа и отката.

### Шаг 5. Успешное обновление

Повторите выпуск без искусственного отказа:

```bash
python scripts/release_manager.py deploy   --tag candidate   --expected-version 1.1.0
```

Проверьте новую версию через `/health`, `/ready` и `/predict`.

### Шаг 6. Критерии отката

Сформулируйте не менее четырёх критериев. Обязательные категории:

- сервис не достигает состояния ready за установленное время;
- smoke-тест возвращает ошибку;
- версия в `/health` не соответствует ожидаемой;
- API нарушает контракт ответа;
- дополнительно: рост latency, ошибки 5xx, ухудшение метрики модели, нарушение схемы данных.

### Шаг 7. Журнал и постмортем

Подготовьте короткий отчёт:

- цель и состав выпуска;
- последовательность событий;
- симптом и способ обнаружения;
- причина искусственного отказа;
- выполненный откат;
- подтверждение восстановления;
- меры, предотвращающие повторение реального инцидента.

## 5. Представляемый результат

1. два локальных образа с разными тегами;
2. менеджер релизов либо эквивалентный воспроизводимый сценарий;
3. лог неуспешного выпуска и отката;
4. лог успешного обновления;
5. политика версионирования и критерии отката;
6. `release-history.jsonl` или эквивалентный журнал;
7. краткий постмортем;
8. история Git и индивидуальная демонстрация.

## 6. Критерии оценивания — 5 баллов

| Критерий | Баллы |
|---|---:|
| Стабильная и кандидатная версии однозначно идентифицируются | 0.75 |
| Кандидат автоматически проверяется health/readiness/smoke-тестом | 1.0 |
| Неуспешный выпуск воспроизводимо приводит к возврату стабильной версии | 1.5 |
| Критерии отката и журнал релиза содержательны и не раскрывают секреты | 0.75 |
| Успешное обновление и индивидуальное объяснение выполнены корректно | 1.0 |

### Критические ошибки

- стабильная версия перезаписывается без сохранения тега;
- откат выполняется только устным описанием;
- после отката сервис не проверяется повторно;
- секреты добавляются в образ, `.env`, журнал или Git;
- студент не может объяснить, почему выпуск был признан неуспешным.

## 7. Сценарий защиты

Преподаватель выбирает один вариант:

1. изменить ожидаемый номер версии и определить, почему smoke-тест не проходит;
2. включить искусственный startup failure и выполнить откат;
3. изменить порт публикации без изменения порта приложения;
4. повредить путь к модели и локализовать ошибку;
5. изменить одну проверку readiness и объяснить последствия.

## 8. Использование генеративного ИИ

Допускается помощь при написании скриптов и постмортема. Не допускается скрытое использование ИИ вместо демонстрации. Студент отвечает за безопасную обработку переменных окружения, корректность команд и интерпретацию журнала выпуска.

## Использование внешних ресурсов и командная работа

- разрешены материалы курса и официальная документация используемых инструментов;
- сторонние статьи, примеры и фрагменты кода допускаются при указании источника и самостоятельной адаптации;
- запрещено выдавать чужой репозиторий или готовое решение за собственную работу;
- секреты, токены, персональные данные и закрытый код нельзя передавать внешним сервисам;
- при командной работе каждый участник фиксирует вклад в Git и проходит индивидуальную защиту;
- преподаватель вправе ограничить Интернет на отдельном этапе защиты или выдать эквивалентный локальный материал.
