# Лабораторная работа №6. ML-сервис в Docker Compose

## 1. Назначение

Сформировать навык упаковки модели машинного обучения в переносимый сервис инференса и обеспечить воспроизводимый запуск через Docker Compose.

## 2. Проверяемые результаты

| Индикатор | Уровень | Наблюдаемый результат |
|---|---|---|
| LC-5.1 | средний | Студент создаёт и запускает контейнеризированный ML-сервис, использует healthcheck и автоматическую smoke-проверку. |
| LC-3.1 | средний | Студент объясняет архитектуру API, модельного артефакта, контейнера и Compose-конфигурации. |

## 3. Исходные материалы

- базовый проект `resources/starter-project/project-baseline/`;
- обучающая и инференсная части из предыдущих лабораторных;
- контракт данных `configs/data_contract.json`;
- готовая либо самостоятельно обученная модель;
- шаблоны `Dockerfile`, `.dockerignore`, `compose.yaml` и smoke-теста.

## 4. Условия выполнения

- Python 3.11 или совместимая версия;
- Docker Engine / Docker Desktop с поддержкой `docker compose`;
- не менее 2 ГБ свободного дискового пространства;
- подключение к Интернету требуется только при первой загрузке базового образа и зависимостей;
- GPU и платные облачные сервисы не используются.

## 5. Задание

### Шаг 1. Проверка локального приложения

1. Сформируйте данные и обучите базовую модель.
2. Запустите API локально.
3. Проверьте endpoint:
   - `GET /health`;
   - `GET /ready`;
   - `POST /predict`;
   - OpenAPI-документацию `/docs`.
4. Зафиксируйте пример корректного и некорректного запроса.

### Шаг 2. Контейнеризация

Подготовьте `Dockerfile`, который:

- использует официальный Python-образ;
- устанавливает только необходимые зависимости;
- формирует или включает модельный артефакт воспроизводимым способом;
- задаёт `MODEL_PATH` и метаданные версии;
- запускает приложение на `0.0.0.0:8000`;
- выполняется от непривилегированного пользователя;
- содержит проверку готовности либо совместим с healthcheck из Compose.

### Шаг 3. Исключение лишних файлов

Настройте `.dockerignore`. В контекст сборки не должны попадать:

- `.git`, виртуальное окружение и кэши;
- `mlflow.db`, `mlruns`, DVC cache;
- `.env` и файлы с секретами;
- локальные логи и временные артефакты.

### Шаг 4. Docker Compose

Создайте `compose.yaml`, который:

- запускает сервис `api`;
- публикует порт, задаваемый переменной `API_PORT`;
- использует тег образа из `API_TAG`;
- передаёт только несекретные настройки;
- содержит healthcheck;
- имеет политику перезапуска;
- при включении профиля `validation` запускает одноразовый сервис `smoke` после готовности API.

### Шаг 5. Сборка и проверка

Выполните:

```bash
cp .env.example .env
docker compose config
docker compose build api
docker compose up -d api
python scripts/smoke_test.py --base-url http://127.0.0.1:8000
docker compose --profile validation run --rm smoke
docker compose ps
```

Проверьте, что:

- контейнер получает статус `healthy`;
- `/ready` подтверждает загрузку модели;
- `/predict` возвращает класс и вероятность;
- приложение не зависит от локального виртуального окружения;
- после `docker compose down` сервис можно воспроизвести теми же командами.

### Шаг 6. Документирование архитектуры

Добавьте в отчёт схему:

```text
клиент -> опубликованный порт -> контейнер API -> модельный артефакт
                                  |-> /health
                                  |-> /ready
                                  |-> /predict
```

Объясните различие между образом, контейнером, Compose-сервисом, healthcheck и smoke-тестом.

## 7. Критерии оценивания — 5 баллов

| Критерий | Баллы |
|---|---:|
| Образ собирается воспроизводимо, сервис запускается одной командой | 1.5 |
| `/health`, `/ready`, `/predict` и OpenAPI работают корректно | 1.0 |
| Compose-конфигурация содержит healthcheck и не раскрывает секреты | 1.0 |
| Smoke-тест автоматически проверяет доступность и инференс | 0.75 |
| README, архитектурная схема и индивидуальное объяснение | 0.75 |

### Критические ошибки

Работа не может быть принята без исправления, если:

- API доступен только изнутри контейнера;
- модель отсутствует либо не загружается;
- секреты или `.env` добавлены в Git;
- проверка выполняется только вручную;
- студент не может объяснить назначение основных инструкций Dockerfile и Compose.

## 9. Использование генеративного ИИ

Допускается подготовка черновиков Dockerfile, Compose и README. Студент обязан:

- указать использованный инструмент и характер помощи;
- проверить команды в чистом окружении;
- не передавать модели секреты и персональные данные;
- понимать каждую инструкцию и исправить найденные риски;
- самостоятельно выполнить демонстрацию и изменение по запросу преподавателя.

## Использование внешних ресурсов и командная работа

- разрешены материалы курса и официальная документация используемых инструментов;
- сторонние статьи, примеры и фрагменты кода допускаются при указании источника и самостоятельной адаптации;
- запрещено выдавать чужой репозиторий или готовое решение за собственную работу;
- секреты, токены, персональные данные и закрытый код нельзя передавать внешним сервисам;
- при командной работе каждый участник фиксирует вклад в Git и проходит индивидуальную защиту;
- преподаватель вправе ограничить Интернет на отдельном этапе защиты или выдать эквивалентный локальный материал.
