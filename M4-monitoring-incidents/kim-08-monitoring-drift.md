# Лабораторная работа №8. Мониторинг и анализ дрейфа

## 1. Назначение

Сформировать навык организации наблюдаемости ML-сервиса и интерпретации технических и модельных сигналов без автоматического отождествления любого изменения данных с деградацией модели.

## 2. Проверяемые результаты

| Индикатор | Уровень | Наблюдаемый результат |
|---|:---:|---|
| LC-5.1 | С | Настраивает сбор и визуализацию метрик работающего ML-сервиса. |
| LC-2.1 | С | Сравнивает эталонные и текущие данные, оценивает drift и изменение качества модели. |

## 3. Исходные материалы

- базовый проект `resources/starter-project/project-baseline`;
- `data/production_normal.csv` — штатный поток;
- `data/production_drift.csv` — контролируемое изменение распределения;
- конфигурации `monitoring/prometheus` и `monitoring/grafana`;
- скрипты `generate_traffic.py` и `analyze_drift.py`.

## 4. Условия выполнения

- Python 3.11+;
- Docker Engine или Docker Desktop с Docker Compose;
- CPU, не менее 4 ГБ свободной оперативной памяти;
- отсутствие обязательного доступа к GPU или платному облаку.

При невозможности локального запуска Docker преподаватель предоставляет учебную VM либо заранее сформированный набор метрик. Анализ drift и подготовка отчёта всё равно выполняются индивидуально.

## 5. Задание

1. Установить зависимости, сформировать данные и обучить базовую модель.
2. Запустить API совместно с Prometheus и Grafana:

   ```bash
   cp .env.example .env
   docker compose --profile monitoring up -d --build
   ```

3. Убедиться, что доступны:
   - API: `http://127.0.0.1:8000/health`;
   - метрики: `http://127.0.0.1:8000/metrics`;
   - Prometheus: `http://127.0.0.1:9090`;
   - Grafana: `http://127.0.0.1:3000`.
4. Сформировать штатный трафик по `production_normal.csv`, затем трафик по `production_drift.csv`.
5. На дашборде проверить:
   - интенсивность запросов;
   - долю ошибок;
   - p95 времени ответа;
   - распределение классов и вероятностей;
   - готовность модели.
6. Выполнить офлайн-сравнение данных:

   ```bash
   python scripts/analyze_drift.py      --reference data/production_normal.csv      --current data/production_drift.csv      --output-dir reports/drift
   ```

7. Объяснить, какие признаки изменились, превышен ли порог PSI и повлияло ли изменение на F1-score.
8. Сформулировать решение: продолжить наблюдение, запросить новые метки, переобучить модель или выполнить откат. Решение должно опираться на наблюдаемые данные.

## 6. Представляемый результат

- работающий контур `API → Prometheus → Grafana`;
- скриншот или экспорт учебного дашборда;
- `reports/drift/drift-report.json` и `drift-report.md`;
- краткое инженерное заключение до 1 страницы;
- коммиты с изменениями студента и декларация использования генеративного ИИ.

## 7. Защита

Студент:

1. демонстрирует `/metrics` и дашборд;
2. показывает нормальный и drift-сценарий;
3. объясняет различие между техническим мониторингом, data drift и ухудшением качества;
4. меняет один порог или PromQL-запрос по заданию преподавателя;
5. обосновывает действие по результатам анализа.

## 8. Критерии — максимум 5 баллов

| Критерий | Баллы |
|---|---:|
| Метрики API корректно экспортируются и собираются Prometheus | 1 |
| Grafana автоматически получает источник и отображает релевантные панели | 1 |
| Drift воспроизводимо моделируется и анализируется | 1 |
| Вывод различает изменение данных и реальную деградацию качества | 1 |
| Результат документирован и индивидуально объяснён | 1 |

## 9. Использование генеративного ИИ

Разрешено для объяснения PromQL, подготовки черновика панели или разбора ошибки конфигурации. В отчёте указываются использованные запросы и выполненная проверка результата. Готовый вывод ИИ без воспроизводимой демонстрации и индивидуального объяснения не засчитывается.

## Использование внешних ресурсов и командная работа

- разрешены материалы курса и официальная документация используемых инструментов;
- сторонние статьи, примеры и фрагменты кода допускаются при указании источника и самостоятельной адаптации;
- запрещено выдавать чужой репозиторий или готовое решение за собственную работу;
- секреты, токены, персональные данные и закрытый код нельзя передавать внешним сервисам;
- при командной работе каждый участник фиксирует вклад в Git и проходит индивидуальную защиту;
- преподаватель вправе ограничить Интернет на отдельном этапе защиты или выдать эквивалентный локальный материал.
