# Промежуточная аттестация: зачёт

Форма промежуточной аттестации — **индивидуальная защита сквозного MLOps-проекта**. Максимальная оценка за зачёт — **22 балла**. Баллы зачёта входят в общую 100-балльную систему дисциплины.

## 1. Цель защиты

Защита должна подтвердить, что студент:

- самостоятельно понимает архитектуру и код проекта;
- способен воспроизвести ключевые этапы жизненного цикла;
- связывает версии кода, данных, эксперимента и модели;
- умеет проверять выпуск, наблюдать сервис и реагировать на инцидент;
- может внести небольшое контролируемое изменение без готовой инструкции;
- прозрачно документирует командный вклад и использование генеративного ИИ.

## 2. Допуск к защите

Студент допускается при выполнении всех условий:

1. защищены 9 лабораторных работ;
2. предоставлена ссылка на репозиторий и зафиксирован Git SHA/тег;
3. заполнен [чек-лист сдачи](../Project/submission-checklist.md);
4. проект воспроизводится по README;
5. отсутствуют опубликованные секреты;
6. доступен сценарий drift/инцидента;
7. для командной работы описан и подтверждён индивидуальный вклад.

При технической неисправности, не зависящей от студента, преподаватель может использовать заранее подготовленную локальную копию защищаемого коммита. Это не отменяет индивидуальную демонстрацию понимания.

## 3. Структура защиты

Рекомендуемая продолжительность — **18–25 минут на студента**:

| Этап | Время | Содержание |
|---|---:|---|
| Идентификация версии | 1–2 мин | URL, Git SHA/тег, состав команды, индивидуальный вклад |
| Архитектура | 2–3 мин | компоненты, потоки данных и артефактов, ключевые решения |
| Воспроизводимая демонстрация | 6–8 мин | тесты, DVC/MLflow, API, контейнеризация, мониторинг |
| Инцидент / реакция | 3–4 мин | доказательства, гипотезы, решение, восстановление |
| Индивидуальные вопросы | 3–5 мин | вопросы по индикаторам и конкретным файлам проекта |
| Живое изменение | 3–5 мин | небольшая модификация, тест и объяснение результата |

Преподаватель может сократить повторяющиеся демонстрации, если доказательства уже получены на рубежных защитах, но вопросы и живое изменение остаются обязательными.

## 4. Рубрика на 22 балла

### 4.1. Воспроизводимость проекта — 0–4 балла

| Балл | Дескриптор |
|---:|---|
| 0 | Проект не запускается, команды отсутствуют или результат зависит от скрытых ручных действий. |
| 1 | Запускается отдельный компонент, но данные, окружение или модель не воспроизводятся. |
| 2 | Основной сценарий запускается после существенной ручной помощи; часть версий или конфигураций не зафиксирована. |
| 3 | Проект воспроизводится по README; имеются отдельные некритические неточности или лишние ручные шаги. |
| 4 | Чистое окружение, данные, обучение и сервис воспроизводятся документированными командами; версии и конфигурации однозначны. |

### 4.2. Тестирование и CI — 0–4 балла

| Балл | Дескриптор |
|---:|---|
| 0 | Автоматические проверки отсутствуют или формальны. |
| 1 | Проверяется только часть кода; CI не влияет на качество изменений. |
| 2 | Есть тесты нескольких компонентов, но отсутствуют негативные сценарии или обязательный quality gate. |
| 3 | Код, данные, модель и API проверяются; CI работает, но покрытие сценариев или доказательство блокировки неполны. |
| 4 | Содержательные позитивные и негативные проверки выполняются локально и в CI; некорректное изменение гарантированно блокируется. |

### 4.3. Данные, модели и эксперименты — 0–4 балла

| Балл | Дескриптор |
|---:|---|
| 0 | Версии данных и модели не прослеживаются, эксперименты не воспроизводятся. |
| 1 | Сохранены отдельные файлы или метрики без связи с кодом и данными. |
| 2 | DVC или MLflow используется частично; сравнение запусков либо выбор модели слабо обоснованы. |
| 3 | Версии и запуски связаны; модель выбрана по метрикам, но lineage или quality gate документированы неполно. |
| 4 | Git, DVC, параметры, MLflow Run ID и версия модели связаны; выбор основан на сопоставимых экспериментах и заранее объявленном quality gate. |

### 4.4. API, контейнеризация и развёртывание — 0–4 балла

| Балл | Дескриптор |
|---:|---|
| 0 | Сервис не разворачивается или API не выполняет инференс. |
| 1 | API работает только локально без проверяемого контейнерного сценария. |
| 2 | Контейнер запускается, но readiness, smoke-проверка, конфигурации или откат реализованы частично. |
| 3 | API и Compose работают; обновление/откат демонстрируются с отдельными некритическими недостатками. |
| 4 | Валидируемый API, health/readiness, контейнеры, smoke-test, критерии допуска, версионированный выпуск и предсказуемый откат работают как единый сценарий. |

### 4.5. Мониторинг и реагирование — 0–4 балла

| Балл | Дескриптор |
|---:|---|
| 0 | Метрики отсутствуют, инцидент не диагностирован. |
| 1 | Есть отдельный график или симптом без анализа причины и восстановления. |
| 2 | Мониторинг работает частично; drift или снижение качества рассчитаны без надёжной интерпретации. |
| 3 | Инцидент диагностирован и система восстановлена, но доказательства, повторная проверка или профилактика неполны. |
| 4 | Релевантные технические и ML-сигналы позволяют подтвердить корневую причину; реакция соразмерна риску, восстановление доказано тестами и метриками, постмортем содержит профилактику. |

### 4.6. Документация и индивидуальная защита — 0–2 балла

| Балл | Дескриптор |
|---:|---|
| 0 | Документация не соответствует проекту; студент не объясняет решения или индивидуальный вклад. |
| 1 | Основные документы есть, но ответы требуют существенных подсказок либо живое изменение выполняется частично. |
| 2 | Архитектура, README, история Git и использование ИИ прозрачны; студент самостоятельно отвечает и корректно выполняет живое изменение. |

Машиночитаемая версия весов приведена в [`scoring.json`](scoring.json).

## 5. Обязательные условия

Независимо от арифметической суммы баллов зачёт не выставляется, если:

- не выполнена хотя бы одна обязательная лабораторная работа;
- проект не воспроизводится даже после ограниченной диагностической помощи;
- опубликован действующий секрет или закрытые данные;
- студент не способен объяснить происхождение ключевого кода;
- отсутствует подтверждённый индивидуальный вклад в командном проекте;
- студент отказывается выполнять индивидуальный вопрос или живое изменение;
- доказательства были подменены чужим репозиторием или не соответствуют защищаемому Git SHA.

После устранения нарушения назначается повторная защита в порядке, установленном образовательной организацией.

## 6. Индивидуальная составляющая

Даже при командной разработке каждый студент:

1. объясняет общую архитектуру;
2. отвечает минимум на один вопрос по своей зоне и один вопрос по смежной зоне;
3. находит в репозитории конкретную реализацию заявленного механизма;
4. выполняет отдельное живое изменение;
5. объясняет использование ИИ и способ проверки результата.

Протокол приведён в [`individual-defense-protocol.md`](individual-defense-protocol.md), банк вопросов — в [`question-bank.md`](question-bank.md), варианты изменений — в [`live-change-bank.md`](live-change-bank.md).

## 7. Итоговый результат

- **Зачтено:** выполнены обязательные условия дисциплины, суммарный рейтинг не менее 71 балла, защита проекта подтверждает заявленные результаты обучения.
- **Не зачтено:** обязательные условия нарушены либо суммарный рейтинг ниже 71 балла.

Для фиксации результатов преподаватель использует [`assessment-sheet.md`](assessment-sheet.md).
