# Runbook подготовки и проведения дисциплины

Документ предназначен для преподавателя и описывает сквозной порядок действий от получения репозитория до архивирования результатов. Он не заменяет РПД, КИМ и рубрики, а связывает их в последовательность работ.

Смежные материалы: [рекомендации по оцениванию](../teachers-assessment/README.md), [рекомендации по использованию ресурсов](../teachers-resources/README.md), [диагностика типовых проблем](troubleshooting.md), [пример заполнения оценочного листа](assessment-example.md).

## 1. Назначение полной преподавательской версии

Ветка `main` содержит полный комплект: РПД и ФОС, модель измерения, КИМ всех девяти лабораторных работ, рубрики рубежных защит, банк коротких тестов вместе с ключом, банки материалов итоговой защиты, эталонный учебный проект с работающей реализацией и инструменты проверки.

Ветка `student` — демонстрационная поставка без ключей и эталонных решений. Она показывает рекомендуемый состав выдачи и не является средством разграничения доступа: репозиторий публичный. Подробнее — раздел «Версии репозитория» в [корневом README](../../README.md).

Для фактического проведения дисциплины преподаватель создаёт собственную копию репозитория и адаптирует поставку под инфраструктуру и правила образовательной организации.

## 2. Рекомендуемый порядок подготовки

| Этап | Действие | Ориентир по срокам |
|---|---|---|
| 1 | Клонировать репозиторий и подготовить окружение | до начала семестра |
| 2 | Запустить базовые проверки и убедиться, что эталонный проект воспроизводится | до начала семестра |
| 3 | Проверить Docker-контур на учебных машинах | до модуля 3 |
| 4 | Сформировать студенческую поставку и разместить её в инфраструктуре организации | до первого занятия |
| 5 | Согласовать пороги, сроки и правила пересдачи | до первого занятия |
| 6 | Подготовить хранение ключей и эталонных материалов | до первого теста |

## 3. Получение и локальное клонирование

```bash
git clone https://github.com/TimurTKO/fos-mlops-mtuci.git
cd fos-mlops-mtuci
```

Обе ветки после клонирования доступны локально:

```bash
git branch -a
git log --oneline -5
```

Для параллельной работы с преподавательской и студенческой версиями удобно использовать отдельное рабочее дерево вместо переключения веток:

```bash
git worktree add ../student-delivery student
```

## 4. Проверка окружения

Минимальные требования эталонного проекта перечислены в его [README](../../resources/starter-project/project-baseline/README.md): Python 3.11+, Git, CPU без GPU; DVC 3.x и MLflow 3.x для модуля 2; Docker Engine или Docker Desktop с `docker compose` для модулей 3–4.

```bash
python --version
git --version
docker version
docker compose version
```

Установка зависимостей проекта из корня репозитория:

```bash
python -m pip install -e "resources/starter-project/project-baseline[dev]"
```

Для модулей 2–4 дополнительно:

```bash
python -m pip install -e "resources/starter-project/project-baseline[all]"
```

Порты, которые должны быть свободны к модулям 3–4: `8000` (API), `9090` (Prometheus), `3000` (Grafana), `5000` (MLflow UI). Диагностика занятых портов — в [troubleshooting.md](troubleshooting.md).

## 5. Запуск базовых проверок

Эталонная техническая проверка репозитория:

```bash
python tools/validate_repository.py
```

Валидатор проверяет обязательные документы и КИМ, относительные Markdown-ссылки, JSON и YAML, синтаксис учебных скриптов, состав тестового банка и актуальность путей манифеста, а затем формирует данные, обучает модель и запускает тесты эталонного проекта. Docker валидатор не запускает — контейнерный контур проверяется отдельно, порядок описан в [рекомендациях по использованию ресурсов](../teachers-resources/README.md).

Проверка состава студенческой поставки выполняется над её деревом, а не над `main`:

```bash
python tools/check_student_delivery.py --root ../student-delivery
```

Полное описание инструментов — в [tools/README.md](../../tools/README.md).

## 6. Подготовка студенческой поставки

Порядок формирования выдачи от базового проекта описан в [рекомендациях по использованию ресурсов](../teachers-resources/README.md). Настоящий раздел дополняет его механизмом, встроенным в репозиторий.

1. Взять за основу ветку `student` либо сформировать собственную поставку по манифесту [`.student-exclude`](../../.student-exclude).
2. Манифест описывает три категории: материалы, полностью исключаемые из выдачи; файлы-каркасы, включаемые с комментариями `TODO` вместо реализации; материалы, обязательные для поставки.
3. Разместить поставку в инфраструктуре образовательной организации: собственный репозиторий, LMS или закрытая выдача.
4. Подтвердить состав командой `check_student_delivery.py` перед публикацией.
5. Проверить, что относительные ссылки в выдаче не указывают на исключённые материалы.

При добавлении собственных преподавательских файлов внести их пути в секцию `[exclude]` манифеста, иначе они попадут в следующую пересборку поставки.

## 7. Проведение модулей и рубежные защиты

Трудоёмкость и структура зафиксированы в [РПД](../../docs/rpd.md): 108 часов, 18 часов лекций, 36 часов лабораторных работ, четыре модуля по 27 часов. Детальный поурочный план в материалах репозитория отсутствует и настоящим документом не вводится: календарное планирование выполняет образовательная организация.

Опорная последовательность контроля внутри каждого модуля:

| Модуль | Лабораторные работы | Рубежная защита |
|---|---|---|
| [1. Инженерная подготовка и тестирование](../../M1-engineering-testing/README.md) | ЛР1 — 4 балла, ЛР2 — 5, ЛР3 — 5 | [рубрика](../../M1-engineering-testing/rubric-module-1.md) — 6 баллов |
| [2. Воспроизводимость и эксперименты](../../M2-reproducibility-experiments/README.md) | ЛР4 — 5, ЛР5 — 5 | [рубрика](../../M2-reproducibility-experiments/rubric-module-2.md) — 6 баллов |
| [3. Контейнеризация и развёртывание](../../M3-deployment/README.md) | ЛР6 — 5, ЛР7 — 5 | [рубрика](../../M3-deployment/rubric-module-3.md) — 6 баллов |
| [4. Мониторинг и инциденты](../../M4-monitoring-incidents/README.md) | ЛР8 — 5, ЛР9 — 6 | [рубрика](../../M4-monitoring-incidents/rubric-module-4.md) — 6 баллов |

Порядок контроля внутри темы:

1. лекция;
2. соответствующий короткий тест из [банка](../../resources/test-banks/README.md) — 1 балл;
3. выполнение лабораторной работы;
4. защита лабораторной работы;
5. рубежная защита модуля после завершения его лабораторных работ.

Организационная подготовка модулей 3 и 4 — проверка Docker, портов, предварительная загрузка образов, распределение индивидуальных сценариев инцидентов — описана в [методических указаниях](../README.md) и [рекомендациях по использованию ресурсов](../teachers-resources/README.md).

Суммарное распределение: короткие тесты — 9 баллов, лабораторные работы — 45, рубежные защиты — 24, защита проекта — 22. Итог — 100 баллов, порог зачёта — 71 балл.

## 8. Итоговая индивидуальная защита

Регламент приведён в [Exam/README.md](../../Exam/README.md), процедура — в [протоколе индивидуальной защиты](../../Exam/individual-defense-protocol.md).

До защиты преподаватель:

1. проверяет допуск: защищённые девять лабораторных работ, ссылку на репозиторий, зафиксированный Git SHA или тег, заполненный [чек-лист сдачи](../../Project/submission-checklist.md), отсутствие секретов;
2. выбирает один вопрос по основной зоне вклада и один по смежной из [банка вопросов](../../Exam/question-bank.md);
3. выбирает одно живое изменение из [банка изменений](../../Exam/live-change-bank.md);
4. не сообщает студенту заранее конкретные варианты;
5. при командном проекте распределяет разные вопросы и изменения между участниками.

Во время защиты результат фиксируется в [листе оценивания](../../Exam/assessment-sheet.md) по шести критериям на 22 балла. Машиночитаемые веса — в [scoring.json](../../Exam/scoring.json). Пример заполнения с пояснением баллов — в [assessment-example.md](assessment-example.md).

Допустима одна диагностическая подсказка: она учитывается при выставлении дескриптора, но не означает автоматического незачёта. Прямое указание готового исправления означает, что соответствующий элемент индивидуальной защиты не подтверждён.

## 9. Хранение ключей и эталонных материалов

К материалам ограниченного распространения относятся:

- [ключ к коротким тестам](../../resources/test-banks/answer-key.md);
- [банк вопросов итоговой защиты](../../Exam/question-bank.md);
- [банк живых изменений](../../Exam/live-change-bank.md);
- преподавательские методические указания в каталогах `teachers`, `teachers-assessment` и `teachers-resources`;
- эталонная реализация учебного проекта.

Рекомендуемый порядок:

1. хранить эти материалы отдельно от студенческой выдачи, а не полагаться на разграничение внутри одного публичного репозитория;
2. не публиковать ключ в LMS вместе с тестом; при импорте проверять, что правильный вариант не выделяется форматированием или порядком;
3. при повторной попытке теста менять порядок вопросов и вариантов ответов;
4. заполненные оценочные листы содержат персональные данные обучающихся: хранить их в системе, предусмотренной образовательной организацией, и не помещать в репозиторий;
5. перед каждой публикацией выдачи запускать `check_student_delivery.py`.

## 10. Повторная сдача

Основания и порядок определены в [Exam/README.md](../../Exam/README.md): при нарушении обязательного условия зачёт не выставляется независимо от арифметической суммы баллов, а после устранения нарушения назначается повторная защита в порядке, установленном образовательной организацией.

Рекомендации преподавателю:

1. зафиксировать в листе оценивания конкретную причину направления на повторную защиту и требуемый объём доработки;
2. при повторной защите выбрать другой вопрос и другое живое изменение;
3. при повторной сдаче лабораторной работы изменить хотя бы один параметр, файл, порог или причину инцидента, чтобы задание не сводилось к повторению предыдущей попытки;
4. потребовать новый Git SHA или тег и убедиться, что демонстрация соответствует именно ему;
5. сохранить связь повторной попытки с исходными замечаниями.

## 11. Завершение курса и архивирование

После окончания дисциплины:

1. сохранить итоговые ведомости и заполненные листы оценивания в системе образовательной организации;
2. зафиксировать использованную версию материалов: тег или Git SHA собственной копии репозитория;
3. собрать замечания к КИМ, рубрикам и стартовым материалам для следующего запуска;
4. удалить локальные Docker volumes, отчёты, сгенерированные данные, артефакты и временные пароли на учебных машинах;
5. проверить, что в архивируемых материалах не осталось секретов и токенов;
6. при обновлении книги КРМ выполнить порядок, описанный в [data/README.md](../../data/README.md): сначала заменить исходную книгу и зафиксировать контрольную сумму, затем актуализировать связанные материалы.

Полный чек-лист готовности репозитория — в [docs/quality-checklist.md](../../docs/quality-checklist.md).
