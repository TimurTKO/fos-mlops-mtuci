# Диагностика типовых проблем

Документ предназначен для преподавателя и охватывает проблемы, которые чаще всего возникают при подготовке стенда и проведении лабораторных работ. Каждая запись описана по единой структуре: симптом, вероятная причина, диагностика, рекомендуемое решение, чего не следует делать.

Все команды приводятся в том виде, в котором они предусмотрены материалами репозитория. Команды модулей 2–4 выполняются из каталога [`resources/starter-project/project-baseline`](../../resources/starter-project/project-baseline/README.md), команды проверки репозитория — из его корня.

Организационная подготовка занятий описана в [runbook](course-runbook.md) и [рекомендациях по использованию ресурсов](../teachers-resources/README.md).

## 1. Python и виртуальное окружение

### 1.1. Валидатор сообщает об отсутствии PyYAML

- **Симптом:** `python tools/validate_repository.py` завершается сообщением «Не установлен PyYAML» и кодом 2.
- **Вероятная причина:** зависимости проекта не установлены либо установлены в другое окружение.
- **Диагностика:** `python -c "import sys; print(sys.executable)"` и `python -m pip list | grep -i yaml`.
- **Решение:** выполнить из корня репозитория `python -m pip install -e "resources/starter-project/project-baseline[dev]"`.
- **Не следует:** устанавливать PyYAML отдельно в обход остальных зависимостей — валидатор далее использует scikit-learn, pandas, FastAPI и pytest.

### 1.2. `ModuleNotFoundError: mlops_course`

- **Симптом:** `python -m mlops_course.train` или `pytest` не находят пакет.
- **Вероятная причина:** пакет не установлен в режиме editable, а `PYTHONPATH` не содержит каталог `src`.
- **Диагностика:** `python -c "import mlops_course, sys; print(mlops_course.__file__)"`.
- **Решение:** установить пакет командой `python -m pip install -e ".[dev]"` из каталога проекта. Валидатор репозитория добавляет `src` в `PYTHONPATH` самостоятельно, поэтому его успешный запуск не гарантирует, что ручной запуск сработает.
- **Не следует:** копировать модули в корень проекта или менять структуру `src` — на неё опираются задания.

### 1.3. Несовместимая версия Python

- **Симптом:** ошибки установки зависимостей или синтаксические ошибки в аннотациях типов.
- **Вероятная причина:** используется Python старше 3.11; проект объявляет `requires-python = ">=3.11"`.
- **Диагностика:** `python --version`.
- **Решение:** создать окружение на Python 3.11 или новее: `python -m venv .venv` и активация по инструкции README проекта.
- **Не следует:** ослаблять ограничение версии в `pyproject.toml` — это изменение эталонного проекта.

### 1.4. Смешение окружений

- **Симптом:** пакет установлен, но импорт не работает; `pip` и `python` ведут себя несогласованно.
- **Вероятная причина:** активировано одно окружение, а команда выполняется другим интерпретатором.
- **Диагностика:** сравнить вывод `python -c "import sys; print(sys.executable)"` и `python -m pip --version`.
- **Решение:** всегда вызывать pip через активный интерпретатор: `python -m pip ...`.
- **Не следует:** использовать глобальный `pip` при активированном виртуальном окружении.

## 2. Windows, WSL и Linux

### 2.1. Не активируется виртуальное окружение в PowerShell

- **Симптом:** `.venv\Scripts\Activate.ps1` завершается сообщением о запрете выполнения сценариев.
- **Вероятная причина:** политика выполнения PowerShell.
- **Диагностика:** `Get-ExecutionPolicy -List`.
- **Решение:** разрешить выполнение для текущего пользователя средствами, принятыми в образовательной организации, либо использовать `.venv\Scripts\activate.bat` в cmd.
- **Не следует:** отключать политику выполнения на уровне машины на общих учебных компьютерах.

### 2.2. Проект расположен в файловой системе Windows при работе через WSL

- **Симптом:** заметно медленная установка зависимостей, сборка образа и запуск тестов.
- **Вероятная причина:** каталог проекта находится в `/mnt/c/...`, доступ к нему из WSL происходит через прослойку.
- **Диагностика:** `pwd` внутри WSL.
- **Решение:** клонировать репозиторий в домашний каталог WSL, например `~/fos-mlops-mtuci`.
- **Не следует:** одновременно работать с одним и тем же рабочим деревом из Windows и из WSL.

### 2.3. WSL исчерпывает память при запуске контура мониторинга

- **Симптом:** контейнеры завершаются без явной ошибки приложения, Docker Desktop сообщает о нехватке ресурсов.
- **Вероятная причина:** лимиты виртуальной машины WSL.
- **Диагностика:** `wsl --status`, `free -h` внутри WSL, вкладка Resources в Docker Desktop.
- **Решение:** увеличить лимиты памяти в файле `%UserProfile%\.wslconfig` и выполнить `wsl --shutdown`, затем повторно запустить Docker Desktop.
- **Не следует:** запускать профиль `monitoring` одновременно с другими тяжёлыми контейнерами на учебной машине с малым объёмом памяти.

## 3. Docker Desktop и Docker daemon

### 3.1. Клиент есть, демон недоступен

- **Симптом:** `docker version` выводит только секцию Client; `docker info` завершается ненулевым кодом с сообщением о невозможности подключиться к `npipe` или `unix:///var/run/docker.sock`.
- **Вероятная причина:** Docker Desktop не запущен либо не завершил инициализацию движка.
- **Диагностика:** `docker info`; в Docker Desktop — состояние «Engine running».
- **Решение:** запустить Docker Desktop и дождаться готовности движка; на Linux — убедиться, что служба демона активна.
- **Не следует:** повторять сборку в цикле до готовности демона: диагностическое сообщение при этом теряется.

### 3.2. Выбран Windows-движок вместо Linux

- **Симптом:** сборка образа `python:3.11-slim` завершается ошибкой несовместимости платформы.
- **Вероятная причина:** Docker Desktop переключён в режим Windows containers.
- **Диагностика:** `docker info` и строка с типом ОС сервера.
- **Решение:** переключиться на Linux containers в меню Docker Desktop.
- **Не следует:** подбирать другой базовый образ — `Dockerfile` относится к эталонному проекту.

### 3.3. Долгая первая сборка и загрузка образов

- **Симптом:** первый запуск профиля `monitoring` занимает продолжительное время.
- **Вероятная причина:** загружаются образы `python:3.11-slim`, `prom/prometheus:v3.11.2` и `grafana/grafana:13.0.3`, а на стадии сборки формируются данные и обучается модель.
- **Диагностика:** `docker images` и вывод сборки.
- **Решение:** заранее загрузить образы на учебных машинах, как рекомендовано в [указаниях по проведению модуля 4](../README.md).
- **Не следует:** прерывать первую сборку — незавершённые слои придётся собирать заново.

### 3.4. Ошибка проверки конфигурации Compose

- **Симптом:** `docker compose config` завершается ошибкой подстановки переменных.
- **Вероятная причина:** отсутствует локальный файл `.env`.
- **Диагностика:** `ls -a` в каталоге проекта; сравнение с [`.env.example`](../../resources/starter-project/project-baseline/.env.example).
- **Решение:** создать `.env` из шаблона: `cp .env.example .env`.
- **Не следует:** коммитить `.env` — он исключён `.gitignore` проекта и может содержать локальный пароль Grafana.

## 4. Занятые порты

### 4.1. Порт уже используется

- **Симптом:** контейнер не стартует с сообщением о том, что порт занят; локальный `uvicorn` завершается ошибкой привязки адреса.
- **Вероятная причина:** порт `8000`, `9090`, `3000` или `5000` занят другим процессом или ранее не остановленным контейнером.
- **Диагностика:** `docker ps`; на Windows — `netstat -ano | findstr :8000`; на Linux и в WSL — `ss -ltnp | grep :8000`.
- **Решение:** остановить лишний процесс либо изменить порт публикации в локальном `.env` через `API_PORT`, `PROMETHEUS_PORT`, `GRAFANA_PORT`. Порт MLflow UI задаётся аргументом `--port`.
- **Не следует:** менять внутренние порты сервисов в `compose.yaml` — на них ссылается конфигурация Prometheus.

### 4.2. Остались контейнеры прошлого занятия

- **Симптом:** порты заняты, хотя сервисы, по мнению преподавателя, остановлены.
- **Вероятная причина:** предыдущий запуск завершён закрытием терминала, а не командой остановки.
- **Диагностика:** `docker compose ps` и `docker ps -a`.
- **Решение:** выполнить остановку проекта командой `docker compose --profile monitoring down -v`.
- **Не следует:** удалять контейнеры вручную по одному, оставляя тома и сеть проекта.

## 5. DVC

### 5.1. Каталог не инициализирован

- **Симптом:** команды `dvc` сообщают, что репозиторий DVC не найден.
- **Вероятная причина:** в рабочем проекте студента не выполнена инициализация.
- **Диагностика:** наличие каталога `.dvc` в проекте.
- **Решение:** выполнить `dvc init` в корне проекта студента.
- **Не следует:** копировать служебные каталоги DVC между проектами разных студентов.

### 5.2. `dvc repro` не пересобирает этап

- **Симптом:** после изменения кода или данных этап считается актуальным.
- **Вероятная причина:** изменённый файл не указан в `deps` соответствующего этапа `dvc.yaml`, либо изменён только параметр, не объявленный в `params`.
- **Диагностика:** `dvc status`, `dvc dag`, просмотр [`dvc.yaml`](../../resources/starter-project/project-baseline/dvc.yaml) и [`params.yaml`](../../resources/starter-project/project-baseline/params.yaml).
- **Решение:** дополнить `deps` и `params` этапа; повторить `dvc repro`.
- **Не следует:** принудительно пересобирать всё подряд вместо исправления графа зависимостей: студент не увидит причину.

### 5.3. Remote не настроен

- **Симптом:** `dvc push` или `dvc pull` завершаются ошибкой отсутствия remote.
- **Вероятная причина:** файл `.dvc/config` эталонного проекта намеренно не содержит remote: он настраивается каждым студентом локально.
- **Диагностика:** `dvc remote list`.
- **Решение:** настроить локальный каталог как remote вне Git, как предусмотрено [рекомендациями по использованию ресурсов](../teachers-resources/README.md).
- **Не следует:** сохранять учётные данные удалённого хранилища в `.dvc/config` репозитория.

### 5.4. DVC cache попал в Git

- **Симптом:** резкий рост размера репозитория студента, в индексе появляются бинарные файлы кэша.
- **Вероятная причина:** нарушено правило исключения служебных каталогов.
- **Диагностика:** `git status`, `git count-objects -vH`.
- **Решение:** исключить кэш и сгенерированные данные согласно `.gitignore` проекта, удалить их из индекса и объяснить студенту связь с прослеживаемостью.
- **Не следует:** переписывать историю чужого репозитория за студента — это часть его учебной задачи.

## 6. MLflow

### 6.1. UI не открывается на порту 5000

- **Симптом:** страница по адресу `http://127.0.0.1:5000` не отвечает.
- **Вероятная причина:** процесс `mlflow ui` не запущен либо запущен с другим backend store.
- **Диагностика:** проверить занятость порта; убедиться, что команда запуска соответствует предусмотренной проектом: `mlflow ui --backend-store-uri sqlite:///mlflow.db --port 5000`.
- **Решение:** запустить UI из того же каталога, где находится файл `mlflow.db`, созданный экспериментами.
- **Не следует:** запускать UI из другого каталога и делать вывод об отсутствии запусков: MLflow откроет пустое хранилище.

### 6.2. Запуски не отображаются

- **Симптом:** UI открывается, но эксперимент пуст.
- **Вероятная причина:** несовпадение `--tracking-uri` при запуске экспериментов и `--backend-store-uri` при запуске UI.
- **Диагностика:** сверить аргументы [`scripts/run_experiments.py`](../../resources/starter-project/project-baseline/scripts/run_experiments.py) и команды `mlflow ui`; проверить наличие файла `mlflow.db`.
- **Решение:** использовать одно и то же хранилище в обеих командах.
- **Не следует:** объявлять эксперимент невоспроизводимым до сверки хранилищ.

### 6.3. База заблокирована

- **Симптом:** ошибка блокировки SQLite при параллельных запусках.
- **Вероятная причина:** одновременная запись из нескольких процессов в один файл `mlflow.db`.
- **Диагностика:** проверить, сколько процессов MLflow запущено.
- **Решение:** выполнять серию экспериментов последовательно; для параллельной работы группы использовать отдельные хранилища или учебный tracking server.
- **Не следует:** удалять `mlflow.db` во время активного запуска — потеряется журнал уже выполненных экспериментов.

### 6.4. Сравнение запусков некорректно

- **Симптом:** метрики запусков различаются, но вывод о лучшей модели вызывает сомнение.
- **Вероятная причина:** запуски выполнены на разных версиях тестовой выборки или с разной процедурой расчёта.
- **Диагностика:** сверить зафиксированные версии данных и параметры запусков.
- **Решение:** сравнивать только сопоставимые запуски и оценивать обоснование по заранее объявленному quality gate.
- **Не следует:** засчитывать выбор модели исключительно по максимальному значению метрики.

## 7. FastAPI

### 7.1. `/ready` отвечает 503

- **Симптом:** `/health` доступен, `/ready` возвращает 503.
- **Вероятная причина:** артефакт модели отсутствует по пути `MODEL_PATH` или повреждён.
- **Диагностика:** проверить наличие файла артефакта; посмотреть журнал сервиса, в контейнере — `docker compose logs api`.
- **Решение:** сформировать данные и обучить модель предусмотренными командами `python scripts/generate_data.py --output-dir data` и `python -m mlops_course.train`.
- **Не следует:** считать 503 отказом readiness-проверки как таковой: разделение `/health` и `/ready` — проверяемый результат обучения.

### 7.2. `/predict` возвращает 422

- **Симптом:** корректный на вид запрос отклоняется с кодом 422.
- **Вероятная причина:** число признаков в запросе не равно объявленному в контракте данных, либо передан неверный тип.
- **Диагностика:** сверить запрос с [`data_contract.json`](../../resources/starter-project/project-baseline/configs/data_contract.json); открыть `/docs` и проверить схему.
- **Решение:** передать вектор из объявленного числа числовых признаков.
- **Не следует:** ослаблять валидацию схемы, чтобы «починить» запрос: отделение 4xx от 5xx проверяется в ЛР2 и ЛР8.

### 7.3. Контейнер не переходит в состояние healthy

- **Симптом:** сервис `smoke` не стартует, так как ожидает `service_healthy` у API.
- **Вероятная причина:** healthcheck обращается к `/ready`, а модель в образе недоступна; либо активна учебная переменная моделирования отказа старта.
- **Диагностика:** `docker compose ps`, `docker inspect` по контейнеру API, значение `SIMULATE_STARTUP_FAILURE` в локальном `.env`.
- **Решение:** привести `.env` в соответствие с [`.env.example`](../../resources/starter-project/project-baseline/.env.example) и пересобрать образ.
- **Не следует:** убирать зависимость `smoke` от состояния API — на ней построен сценарий допуска выпуска в ЛР7.

## 8. Prometheus и Grafana

### 8.1. Target в состоянии DOWN

- **Симптом:** на странице targets Prometheus задание `mlops-course-api` не активно.
- **Вероятная причина:** API недоступен внутри сети Compose либо не отдаёт `/metrics`.
- **Диагностика:** открыть `http://127.0.0.1:9090/targets`; проверить `/metrics` у API; сверить цель в [`prometheus.yml`](../../resources/starter-project/project-baseline/monitoring/prometheus/prometheus.yml).
- **Решение:** запускать Prometheus в том же проекте Compose, где работает API; убедиться, что API достиг состояния healthy.
- **Не следует:** заменять внутреннее имя сервиса на `localhost`: внутри контейнера это другой адрес.

### 8.2. Метрики отсутствуют, хотя сервис работает

- **Симптом:** запросы к API выполняются, но счётчики не растут.
- **Вероятная причина:** к сервису не поступало трафика после запуска, либо запросы шли мимо инструментированных endpoint.
- **Диагностика:** выполнить несколько запросов и повторно открыть `/metrics`.
- **Решение:** сформировать базовую картину штатным трафиком до моделирования аномалий, как предусмотрено ЛР8.
- **Не следует:** делать вывод о drift по метрикам, собранным без базовой линии.

### 8.3. Grafana не принимает пароль

- **Симптом:** вход по адресу `http://127.0.0.1:3000` не выполняется.
- **Вероятная причина:** используется значение из шаблона, а не из локального `.env`.
- **Диагностика:** проверить `GRAFANA_ADMIN_USER` и `GRAFANA_ADMIN_PASSWORD` в локальном `.env`.
- **Решение:** задать собственное значение пароля в `.env` до первого запуска.
- **Не следует:** фиксировать реальный пароль в Git, в шаблоне `.env.example` или в отчёте студента.

### 8.4. Дашборд не появился

- **Симптом:** в Grafana нет ожидаемого дашборда или источника данных.
- **Вероятная причина:** том Grafana сохранил предыдущее состояние, либо провижининг не подключён.
- **Диагностика:** `docker compose logs grafana`; проверить состав каталога `monitoring/grafana`.
- **Решение:** остановить проект с удалением томов и запустить профиль `monitoring` заново.
- **Не следует:** оценивать работу студента по внешнему виду дашборда: критерием является корректность выбранных сигналов.

## 9. Относительные пути

### 9.1. Команда не находит данные или контракт

- **Симптом:** ошибки об отсутствии `data/train.csv` или `configs/data_contract.json`.
- **Вероятная причина:** команда запущена не из каталога проекта: значения по умолчанию у скриптов заданы относительными путями.
- **Диагностика:** `pwd`; сверить аргументы по умолчанию в соответствующем скрипте.
- **Решение:** запускать команды модулей 2–4 из каталога `resources/starter-project/project-baseline`, а проверки репозитория — из его корня; при необходимости передавать пути явными аргументами.
- **Не следует:** менять значения по умолчанию в эталонном проекте.

### 9.2. Неработающая ссылка в Markdown

- **Симптом:** ссылка в документе ведёт на несуществующий файл.
- **Вероятная причина:** материал перемещён или не входит в студенческий комплект.
- **Диагностика:** `python tools/validate_repository.py` — он проверяет все относительные ссылки и указывает файл и цель.
- **Решение:** исправить ссылку либо заменить её пояснением, если материал не входит в соответствующую версию.
- **Не следует:** оставлять в студенческой выдаче ссылки на исключённые преподавательские материалы.

## 10. Окончания строк и права доступа

### 10.1. Git показывает изменения во всех файлах

- **Симптом:** после клонирования или переключения ветки `git status` показывает массовые изменения без правок по существу.
- **Вероятная причина:** различие CRLF и LF; в репозитории нет файла `.gitattributes`, поэтому поведение определяется настройкой `core.autocrlf`.
- **Диагностика:** `git config core.autocrlf`, `git diff --stat`.
- **Решение:** привести настройку `core.autocrlf` к единому значению для всех участников; выполнить повторное клонирование при необходимости.
- **Не следует:** коммитить массовое переоформление файлов вместе с содержательными изменениями.

### 10.2. Отказ в доступе при работе с томами в контейнере

- **Симптом:** сервис не может прочитать примонтированную конфигурацию или записать данные.
- **Вероятная причина:** конфигурации монтируются только для чтения; кроме того, процесс в образе API выполняется от непривилегированного пользователя.
- **Диагностика:** `docker compose logs` соответствующего сервиса; проверка прав в файловой системе хоста.
- **Решение:** выдать права на чтение файлов конфигурации на стороне хоста; для сохраняемого состояния использовать именованные тома, предусмотренные проектом.
- **Не следует:** запускать контейнеры от root ради обхода прав — безопасная конфигурация входит в проверяемый результат ЛР6.

## 12. Безопасная очистка и повторный запуск

Порядок предполагает, что все результаты, которые требуется сохранить, уже выгружены: команда остановки с удалением томов уничтожает состояние Prometheus и Grafana.

1. Остановить проект с удалением томов: `docker compose --profile monitoring down -v`.
2. Убедиться, что контейнеры и сеть проекта удалены: `docker compose ps`.
3. Удалить локальные сгенерированные каталоги проекта: данные, артефакты и отчёты; они исключены `.gitignore` и восстанавливаются командами проекта.
4. При необходимости удалить локальное хранилище экспериментов `mlflow.db` — только если журнал запусков больше не нужен.
5. Проверить, что `.env` не содержит действующих паролей, и при необходимости пересоздать его из `.env.example`.
6. Повторно запустить контур: создание `.env`, проверка `docker compose config`, сборка и запуск нужного профиля.
7. Убедиться в исправности стенда до занятия: доступность `/health` и `/ready`, активный target в Prometheus, вход в Grafana.

**Чего не следует делать при очистке**

- выполнять глобальную очистку Docker на общей учебной машине: это затронет посторонние проекты;
- удалять тома до того, как сохранены доказательства инцидента, которые студент представляет на защите;
- очищать рабочее дерево студента командами, отменяющими его незакоммиченные изменения;
- удалять `data/krm-v3.0.xlsx` и другие исходные материалы репозитория при очистке сгенерированных файлов.
