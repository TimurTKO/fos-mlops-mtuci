# Рекомендации обучающимся

Практические работы выполняются как последовательное развитие одного сквозного репозитория. На защите демонстрируются команды запуска, результаты автоматических проверок, история Git и понимание архитектуры.

## Общий порядок работы

1. Создать отдельную ветку для лабораторной работы.
2. Выполнить задание небольшими логически связанными коммитами.
3. Запустить локальные тесты и обязательные команды воспроизводимости.
4. Обновить README и декларацию использования генеративного ИИ.
5. Создать pull request или подготовить ссылку на ветку для проверки.
6. На защите выполнить запуск и небольшое изменение по заданию преподавателя.

## Модуль 2

После значимого запуска сохранять Git SHA, параметры, `dvc.lock`, хеш данных, MLflow Run ID, метрики и URI модели. Не добавлять в Git DVC cache, `mlflow.db`, `mlruns/`, секреты remote и локальные абсолютные пути.

## Модуль 3

Перед выпуском зафиксировать стабильный тег и критерии отката. Кандидат должен пройти unit/integration tests, readiness и smoke-проверку. `.env` и журналы не публикуются.

## Модуль 4

1. Сначала зафиксировать базовую картину на штатных данных.
2. Не менять одновременно датасет, модель и конфигурацию мониторинга.
3. Отличать HTTP 4xx от 5xx и техническую деградацию от ML-деградации.
4. Не трактовать PSI как доказательство concept drift.
5. Для качества использовать актуальные размеченные данные либо явно указывать отсутствие меток.
6. Сохранять исходные доказательства инцидента до исправления.
7. В постмортеме отделять симптом, корневую причину и предупреждающие меры.

## Сквозной проект и итоговая защита

Перед зачётом необходимо:

1. зафиксировать защищаемую версию Git-тегом или SHA;
2. заполнить [`Project/submission-checklist.md`](../../Project/submission-checklist.md);
3. заполнить декларацию использования ИИ по шаблону;
4. подготовить короткую архитектурную схему и таблицу прослеживаемости;
5. убедиться, что все команды README работают в чистом окружении;
6. подготовить один воспроизводимый сценарий инцидента;
7. быть готовым выполнить небольшое изменение и соответствующую проверку.

На защите оценивается не скорость набора команд, а понимание причин, зависимостей и рисков. Не следует заранее записывать демонстрацию как видео вместо живой проверки. Для длительных операций допускается использовать ранее сформированный артефакт, если студент показывает его связь с кодом, данными и запуском.
